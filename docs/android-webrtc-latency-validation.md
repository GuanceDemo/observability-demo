# Android 网页回显优化验收记录

日期：2026-09-07。目标：GCP `twt-gcp-integration / asia-east2-a /
mall-demo-kvm-emulator-poc`。入口：[真实 APK 演示](https://35.241.68.75.nip.io/business.html?lang=zh&scene=android-storefront&view=mobile)。

## 已落地

- 截图 fetch、解码和定时器归属于可取消的代次；视频恢复或连接更换后，旧响应不能重新覆盖视频。
- 每次实际发送的鼠标、触摸或键盘输入独立触发有界截图刷新，不受统计样本占用影响；`fresh=1` 跳过已完成的缓存，并合并正在进行的捕获。
- 重连替换同类旧轨道；首帧重绘后的重连等待由 700 ms 调整为 3000 ms，避免过早丢弃仍在启动的连接。
- 输入后等待画面变化时，未变化的视频帧不会取消重绘恢复；250 ms 后首次请求，随后每隔 1 秒重试，最多 3 次，仍遵守原有 5 秒测量期限。
- 每次被纳入测量的按下事件并行建立 ACK 游标；64 条有界历史、进程 epoch、5 秒本地截止时间及冲突输入排除，避免复用旧游标。等待期间的历史溢出也返回 409。
- 缓冲和解码使用区间增量；设备轮询不阻塞视频监测，getStats 按连接合并。最近 100 个样本按视频、截图、等待、混合模式分组，超时和排除样本不混入成功分位数。
- 页面显示松开后 ACK 等待、解码/呈帧计数、播放时间和页面可见状态；发布时同步更新翻译脚本和播放器入口版本。
- 提供会话级 `rtcTransport=relay` 诊断选项，默认仍自动选择 ICE。未修改 APK、Emulator 分辨率、渲染器、凭据或数据卷。

## 验证

- 20 项 Node 回归测试通过，覆盖截图异步竞态、独立刷新、ACK 游标/冲突/截止时间、统计重置、轨道替换、慢首帧、未变化帧恢复及网页边界。
- 8 项 Python 测试对实际补丁组装后的 Gateway handler 执行异步验证。
- 30 项 order-service Maven 测试通过；首次沙箱运行受 Mockito JVM 附加限制影响，获准在沙箱外运行后通过。后续网页变更对应的 24 项静态契约测试通过。
- 固定版本上游补丁全部可组装，TypeScript 检查和 Vite 生产构建通过；新增 InputEvent 声明与现有 protobuf 一致。
- `business.html` 内联 JavaScript 解析、Shell 语法和 `git diff --check` 通过。
- GCP 的 Emulator、Gateway、APK 看护、Caddy、coturn 均 active；Compose 服务均 running。ACK cursor 返回 version 2；无效 cursor/fresh 返回 400；fresh PNG 返回真实固定尺寸截图数据。

## 线上观察及限制

早期浏览器标签页位于收起的后台分组中，这一时段不能作为正常前台视频延迟的基准。
用户将演示页置于前台后，重新连接并执行了真实 APK 导航。直连样本曾出现：RTT
约 159–198 ms，单次截图回显 1366.4 ms、ACK 577.4 ms、下一视频帧超过 5 秒。
这些是排障样本，不是优化前后的受控性能比较。

`latency-v3` 前台会话持续播放，截图层正常退出。前三次首页/路线导航的画面变化为
1128.0、1510.9、732.6 ms，其中两次 ACK 为 343.8、336.4 ms，一次 ACK 超时。
随后购物车导航收到下一帧但画面未变化，超过 5 秒；再点击首页时，视频才显示购物车，
而服务端最近 ACK 已是 `navigate:home`。因此不能把任意画面变化等同于本次目标页面
已出现，也不能把前三个成功样本解释为稳定性已经达标。

这轮复核发现未变化的下一帧会提前取消原有重绘，最终 `latency-v4` 修订了这一条件，
加入最多 3 次有界重试，并新增两项回归测试。首次连接约 6 秒内展示真实视频，
截图层退出，页面 visible；首帧重连等待为 3000 ms。

最终版前台复测（16:40–16:42，STUN srflx → srflx，RTT 约 121–124 ms）：

| 导航目标 | 下一视频帧 | 首个画面变化 | APK ACK | 画面人工核对 |
| --- | ---: | ---: | ---: | --- |
| 阅读路线 | 818.6 ms | 2693.8 ms | 342.3 ms | 正确显示路线 |
| 购物车 | 1097.6 ms | 1097.6 ms | 超过 5 秒 | 正确显示购物车 |
| 首页 | 777.1 ms | 777.1 ms | 超过 5 秒 | 正确显示首页 |

这三个视频样本没有画面变化超时，但只构成一次短会话的功能验收。延迟为
0.78–2.69 秒，仍有明显波动；两次 ACK 测量超时不能解释成导航失败。界面显示
的视频 p50/p95 为约 1098/2694 ms，仅来自这三个成功样本，不足以证明性能改善。

请求 relay 的一轮连接报告了 prflx → host 的候选路径，未取得可靠的纯 TURN 与
直连性能对照，不能据此声称中继更快，也没有改全局默认策略。尚无足够前台视频
样本证明稳定的 p95 改善；界面已有的分位数功能不等于已完成性能基准。

ACK 是保守的单客户端关联，未把浏览器输入 ID 贯穿到 APK；外部并发客户端及
延迟 Logcat 仍是限制。原生 onPress 很快、早于 HTTP 游标建立时，样本可能超时，
不能把它解释成业务执行失败。APK 选择器只处理 6 本书，现有证据不足以把原生
重计算认定为主要瓶颈，本次未为此重建 APK。
