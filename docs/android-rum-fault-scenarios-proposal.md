# Android RUM 与会话重放故障场景调整方案

日期：2026-09-08。状态：建议稿，本次未修改应用或部署。

## 目标与范围

围绕一次真实购书操作，展示“用户遇到问题 → RUM 发现异常或异常行为 → 回放还原操作 →
结合错误、性能、请求及日志定位 → 验证修复”的过程。

仅调整 Android 演示的 `frontend / runtime / network` 三层。建议中文显示为
“前端体验 / 运行时 / 网络请求”，内部 layer 值不变。
后面 `service / dependency / jvm` 三层的场景、注入行为、恢复行为及链路保持不变。
共享目录中的 Web 场景不随本次调整。

## 现有实现与不足

- `mobile-app/src/faults.ts`：白屏是主动清空根视图并在 5 秒后恢复；JS 异常由定时器直接
  抛出；慢网络独立请求 `slow-resource`。用户只操作故障抽屉就能触发，缺少业务前因后果。
- `mobile-app/src/api.ts`：慢请求为 `/api/demo/slow-resource?delayMs=2600`，可以产生
  Resource，但目前没有对应的图书内容加载、等待、失败、重试状态。
- `DemoFaultsModule.kt`：Safe 包拒绝 Crash 和主线程阻塞。当前 runtime 缺少适合常规
  演示的、可恢复且有时长上限的原生卡顿场景。
- `mobile-app/src/observability.ts`：自定义 Error 把 message 同时作为 stack 传递，
  这部分数据不足以展示真实源码定位；自动捕获的异常需另行核对。
- `FaultDrawer.tsx` / `traceLink.ts`：目前只有 Trace 入口。纯前端问题可能没有服务端
  Trace，需要从 RUM 会话和回放开始查看。

## 推荐场景

所有常规场景先“启用”，再由指定业务动作触发。故障面板提前说明触发步骤和预期观察，
商城页面保持真实产品反馈，技术原因放在演示说明和观测数据中。

### 前端体验

| 场景 | 业务触发与实际现象 | 预期证据 | 修复方向 |
| --- | --- | --- | --- |
| 商品详情渲染失败 | 打开指定图书，缺失字段使真实详情渲染抛错；ErrorBoundary 展示可重试错误区域，保留导航 | Replay 展示首页→指定商品→错误区域；RUM Error 带真实 JS/组件堆栈、商品和 View 上下文；对应版本 SourceMap 可还原源码 | 数据边界校验、空值处理、组件错误隔离 |
| 加购无反馈 | 点击“加入购物车”，某状态分支未完成状态更新，角标和购物车不变化；用户再次尝试 | Replay 展示实际点击与缺失反馈；业务 Action、加购前后数量和结果校验日志解释问题。可以没有原生异常和网络失败 | 修复状态分支、操作结果反馈，确保操作结果与 UI 一致 |
| 购物车金额未更新 | 修改数量或删除一本书后，行项目更新，合计仍使用旧值；停在提交订单之前 | Replay 展示数量与合计不一致；Action 记录数量变化；自定义业务校验记录预期/实际金额 | 修复派生状态与依赖，恢复后用相同操作验证合计 |

前两项分别承担“有异常堆栈”和“没有异常堆栈”的主要演示。
RUM 不会自动理解“加购应该增加一本”或“金额计算错误”；这些需要应用提供业务结果校验。
连续点击可以通过回放观察或应用自定义统计展示，不预设当前移动 SDK 具备自动愤怒点击识别。

原来的独立白屏和无业务上下文 JS 抛错不作为常规主场景。详情渲染失败保留了页面不可用与
JS 定位的展示价值，同时支持继续操作、重试和恢复。

### 运行时

| 场景 | 业务触发与实际现象 | 预期证据 | 修复方向 |
| --- | --- | --- | --- |
| 结算预览卡顿 | 打开结算预览时，受控的同步工作占用 Android 主线程约 1.5–2 秒，随后自动恢复 | 原生 Long Task/UI Block 的真实持续时间和堆栈；Replay 中操作前后的画面与等待；请求正常或没有相关慢请求 | 把同步工作移出 UI 线程、拆分任务、缓存结果 |
| Android ANR（进阶） | 在已有危险演示包中，通过正常业务入口触发较长原生阻塞，并继续操作 | SDK 实际采集到的 ANR/阻塞堆栈与操作前上下文；以平台实际事件为准 | 查找主线程 I/O、锁等待或同步调用 |
| Native Crash（进阶） | 进入指定业务页面触发真实原生异常，重启恢复 | Crash 堆栈、符号化结果、崩溃前已保存的回放片段和重启记录 | 原生参数检查、线程/生命周期与异常处理 |

常规卡顿新增独立、固定时长、单次触发、带冷却的受控实现；保留 Safe 包对现有
Crash/ANR 危险入口的限制，不通过解除整个 `DEMO_FAULTS_ENABLED` 限制开放它们。
两秒 UI 卡顿不能标为 ANR，JS 线程阻塞也不能直接当成 Android 主线程 Long Task。

长阻塞和崩溃时，Replay 未必能保存全过程或最后一帧。验收使用实际上传的片段，结合
原生错误/长任务证据，不要求生成不可能采集的画面。重启前后用持久化演示 run ID 关联，
不假设 SDK session ID 一定保持不变。

### 网络请求

| 场景 | 业务触发与实际现象 | 预期证据 | 修复方向 |
| --- | --- | --- | --- |
| 图书内容加载慢 | 打开图书内容区域，真实请求耗时约 3–5 秒，显示可见加载过程，最终成功 | Replay 中的加载等待与 RUM Resource 持续时间一致；有 Trace 时进一步区分耗时所在位置 | 超时预算、缓存/预加载、减少传输、明确加载反馈 |
| 请求超时与重试 | 同一类只读业务请求达到实际客户端截止时间，显示失败与重试；恢复后重试成功 | 同一业务操作的请求、失败、重试和成功记录；真实错误类型和每次尝试的耗时；Replay 展示整个过程 | 合理的截止时间、取消和有界重试、可理解的失败反馈 |
| 封面或试读资源失败 | 打开指定内容时，真实资源请求返回 404，出现占位/重试；恢复后正常加载 | 404 Resource 与页面资源缺失在时间上对应；可定位 URL、商品、页面和恢复结果 | 资源地址/版本校验、备用资源和降级 |

“网络请求”表示从客户端请求体验切入，不预判根因一定在网络。沿用服务端 delay 的实现时，
名称应为“请求慢响应”，在 Trace 中如实显示服务端等待；不能宣称是弱网、丢包或 DNS 故障。
不能用 fetch 前后 JS sleep 伪造 Resource 耗时，也不能只伪造一条网络错误记录。

若需要新增图书内容或封面的演示端点，限定为受控只读端点；状态按请求/演示实例隔离，
不切换后面三个层级的全局故障。故障只影响目标业务请求，RUM/Replay 上报、WebRTC、
恢复接口保持可用。真实客户端 deadline 导致取消时，保留 SDK 的实际错误分类，同时标记
`timeout_source=app_deadline`，不杜撰 HTTP 状态码。自动重试优先限定只读请求。

## 演示流程与面板

1. 选场景：显示一句用户症状、一条触发步骤、一条本次观测重点。
2. 启用：面板显示“已就绪，打开指定图书/执行指定操作后触发”；用户收起抽屉正常操作。
3. 发生问题：保留加载、错误区域、购物车状态等实际反馈，允许观察前后过程。
4. 查看证据：提供“本次 RUM”“会话回放”，有真实 Trace 时再提供“请求链路”。
5. 恢复基线并重试：用同一本书、同一操作重跑，记录恢复后的结果。

抽屉状态建议为：未启用 → 已就绪 → 已触发 → 已恢复；恢复不自动清除本轮观测入口。
接口入口需经过当前观测云控制台验证；若暂时拿不到稳定回放深链，则进入按本次 run ID
和时间筛选的 RUM 会话，让用户从会话打开回放。没有数据时显示真实等待状态。

“恢复基线”表示关闭演示故障，不等同于已经发布了源码修复。每个场景的说明单独列出
实际修复方法；若演示真实修复效果，应提供对应代码变更/构建版本及复测结果。

## 观测数据的共同要求

- 每次演示生成 `fault_run_id`；同时记录 `fault_id`、`fault_layer`、`fault_phase`、
  业务动作与商品标识。原生 SDK 的 `session_id/view_id` 保持由 SDK 管理。
- 业务 Action、受控自定义 Error、日志及请求补充同一轮上下文；请求继续使用已有
  `biz_request_id` 和 Trace headers。不要依赖多个快速连续 `startAction` 自动一一关联；
  已安装 SDK 对 Action 存在时间/并发限制。
- 自定义异常传真实 `error.stack` 和必要的组件栈；自动捕获和 ErrorBoundary 手动上报
  做去重。SourceMap、R8 mapping 与实际 APK 版本严格对应。
- 业务逻辑错误用业务校验和上下文解释，明确与 SDK 自动采集的错误区分。
- 只采集本 Demo 的合成身份、公开图书素材和必要业务字段；新增网络资源在 Replay
  中验证图片和文字的真实重建效果。
- WebRTC 接收/播放延迟作为传输层诊断保留；原生卡顿验收以 APK RUM Long Task 和
  原生时间为准，不用外层浏览器视频 FPS 或回显耗时替代。

## 实施顺序与验收建议

第一批做六个常规场景：详情渲染失败、加购无反馈、金额未更新、可恢复原生卡顿、
内容慢响应、超时重试。同时完成触发状态机、真实堆栈和 RUM/回放入口。
第二批补充资源 404，并将已有 Crash/ANR 改为进阶业务入口。

每个场景的交付必须包含：

- 明确且可重复的业务触发步骤，正常基线与注入后都有可核对结果。
- Android Release APK 中真实产生的 RUM 数据和可打开的 Replay，不以 console 日志
  或“注入成功”Toast 代替验收。
- 至少一轮“正常 → 故障 → 恢复”配对演示；观测窗口能看到触发前的操作及恢复后的结果。
- 对应的错误源码位置、状态校验或原生线程证据；不能只有一个预先写好的原因说明。
- 请求失败/超时的实际数据、失败前后时间和重试记录，且不把上报链路一起破坏。
- 后三个层级的目录内容与执行/恢复契约回归，Web 原场景回归。
